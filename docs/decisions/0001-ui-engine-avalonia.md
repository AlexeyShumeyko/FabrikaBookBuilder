# 1. Перенос интерфейса на Avalonia

- Статус: принято
- Дата: 2026-10-03
- Связано с: [0004](0004-avalonia-may-look-different.md)

## Контекст

Текущая оболочка — WPF, `net8.0-windows`, `UseWPF`.

WPF не поддерживает декодирование JPEG с уменьшением: `BitmapImage.DecodePixelWidth`
читает изображение целиком и масштабирует уже после. При исходных файлах в 24 Мпикс
и 200 видимых ячейках это 4,8 гигапикселя декодирования на одно открытие проекта —
измерено 33,8 с в потоке интерфейса, полное открытие проекта 41,9 с при пике памяти
2,35 ГБ.

Альтернативные способы обойти это в WPF:

| Способ | Результат |
|---|---|
| Прямой вызов WIC (`windowscodecs.dll`) | Работает, но код привязан к Windows и не переносится |
| Декодирование на фоновом потоке | Убирает заморозку, но не стоимость: 33,8 с работы остаются |
| Другие движки с масштабированием JPEG | Tauri, Flutter, Electron не имеют .NET-кода проекта |

Avalonia декодирует JPEG с уменьшением через Skia, кроссплатформенно и без
собственного слоя прямых вызовов.

## Решение

Предметная область, правила и сценарии переносятся в `PhotoBook.Core` и
`PhotoBook.Application` без изменений. Интерфейс переписывается в
`PhotoBook.Desktop.Avalonia`; WPF-оболочка `PhotoBook.Desktop.Wpf` остаётся в решении
до прохождения приёмки.

## Последствия

- Сетевой доступ приложения ограничен Windows; macOS требует отдельного распространения.
- Стоимость превью переносится в адаптер `IThumbnailProvider`: та же логика, другая
  реализация.
- Интерфейс переписывается, а не переносится: оценка — по экранам, см. `doc/ROADMAP.md`.
- Формат проекта, имена файлов при выгрузке и поведение сценариев не меняются.

## Проверка перед началом работ

Пробное приложение измеряет время старта, память и время создания превью на тех же
исходных файлах. Перенос прекращается, если превью не становится существенно дешевле.
