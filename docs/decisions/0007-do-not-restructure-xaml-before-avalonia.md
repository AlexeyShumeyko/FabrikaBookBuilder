# 7. Разметку WPF не перестраиваем перед переездом на Avalonia

- Статус: принято
- Дата: 2026-10-13

## Контекст

После волны 2 осталось разделить по смыслу `CombinedModeView.xaml` (899 строк),
`Theme.xaml` (823) и `UniqueFoldersView.xaml` (559). Это последняя крупная работа
волны 2, и она пришлась ровно на момент, когда следующим шагом идёт замена движка
на Avalonia (ADR 0001).

Вопрос, который нужно было решить: это работа, которая переживёт миграцию, или
работа, которая будет выброшена?

Посчитано по репозиторию, а не по общим соображениям. В двенадцати XAML-файлах
оболочки:

| Конструкция | Вхождений | Переносится ли |
|---|---|---|
| `AutomationProperties.Name` | 55 | нет, другой класс и другое дерево доступности |
| `Click=` (обработчики в разметке) | 28 | нет, в Avalonia привязка к команде |
| `Storyboard` | 17 | нет, своя система анимации |
| `SnapsToDevicePixels` | 15 | нет, такого свойства нет |
| `x:Class` + пространство имён WPF | 12 файлов | нет, своё пространство имён |
| `Trigger Property=` | 11 | нет, своя модель триггеров |
| `WindowStartupLocation` | 8 | нет |
| `DropShadowEffect` | 6 | нет, `BoxShadow` с другой семантикой |
| `d:` (пространство имён дизайна) | 6 | нет |
| `RenderOptions.` / `TextOptions.` | 4 | нет |
| pack-URI для шрифтов | 1 | нет, своя загрузка ресурсов |

А вот это переносится и должно быть сохранено как проектное решение:

| Конструкция | Вхождений |
|---|---|
| `Binding` | 220 |
| `DataTemplate` | 21 |
| `ItemsControl` | 39 |
| `MultiBinding` | 14 |
| `RelativeSource` | 14 |
| `Grid` / `StackPanel` (структура) | 376 / 224 |
| `StaticResource` (ссылки на стили) | 636 |

## Решение

1. **Структуру XAML-файлов волны 2 не трогаем.** Разделение `Theme.xaml` на
   словари уже было попробовано и отменено по измеренной причине (ADR 0007
   приложение перестаёт видеть ресурсы через несколько подключённых словарей).
   Разделение вида на несколько `UserControl` было бы той же ошибкой в другой
   форме: это написание WPF-разметки, которая будет удалена.
2. **Проектное решение сохраняем, а не файл.** Если блок разметки должен стать
   шаблоном или отдельным контролом — это записывается в комментарии к тому месту,
   где он находится сейчас, а не выносится в новый файл. Приложение уже размечено
   секциями: «контрольная панель», «список файлов», «книги», «слоты».
3. **Скрипты проверки остаются рабочими.** `AutomationProperties.Name` в разметке
   исчезнет, поэтому скрипты, ищущие элементы через UI Automation, готовятся заранее
   (ADR 0005: тест, написанный до переноса, переживает перенос).

## Границы применимости

Решение касается только **организации файлов и извлечения под-контролов**.
Оно не запрещает:

- править разметку, если это нужно для исправления дефекта;
- переносить логику из разметки в C# — код переезжает целиком;
- убирать дублирование **внутри одного файла**, если это уменьшает файл без
  создания новых XAML-файлов.

## Последствия

- Пункт 19 бэклога закрывается как «не будем, по решению», а не «не смогли».
- Время волны 2 переносится на пункты бэклога, которые переживают миграцию:
  слой `Application`, скрипты проверки, поведение, а не разметка.
- При написании Avalonia-версии разметка пишется заново по карте из комментариев,
  а не переносится файлами. Это дешевле и правильнее, чем перенос с последующей
  переделкой каждого файла.
