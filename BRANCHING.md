# Ветки и релизы — Fabrika BookBuilder Studio

Этот документ описывает, как вести разработку так, чтобы клиенты
**никогда не получали незаконченную сборку**.

---

## ⚠️ Главное правило

Программа при запуске проверяет GitHub Releases и, если там есть релиз
с версией выше текущей, предлагает обновление.
Значит **любой опубликованный релиз = обновление для всех клиентов**.

Ветка, из которой собирается релиз, — **только `master`**.
Из любой другой ветки релиз не собирается в принципе.

---

## Ветки

| Ветка | Назначение | Релиз? |
|-------|-----------|--------|
| `master` | Боевой код. То, что установлено у клиентов. | **Да** |
| `develop` | Текущая разработка. Точка интеграции фич и фиксов. | Нет |
| `feature/<что>` | Новая функциональность. Создаётся от `develop`. | Нет |
| `fix/<что>` | Обычный багфикс. Создаётся от `develop`. | Нет |
| `hotfix/<что>` | Срочный багфикс у клиентов. Создаётся от `master`. | Нет |
| `release/<версия>` | Подготовка релиза. Создаётся от `develop`. | Нет |
| `chore/<что>` | Инфраструктура, CI, рефакторинг без правок поведения. | Нет |

> **Никогда не создавайте ветку с именем `main`.**
> В старой версии CI релиз собирался из `main` и `master` — это была
> реальная ловушка. Сейчас триггер настроен строго на `master`.

### Схема работы

```
feature/xxx  ──►  develop  ──►  master
   (из develop)      │            ▲
                     │            │
hotfix/yyy ──────────┼────────────┘
   (из master)       │
                     │
   (из develop) ──►  release/1.1.0 ──► master
```

## Обычная работа

```bash
# 1. Новая фича — от develop
git checkout develop
git pull
git checkout -b feature/new-book-format

# ... работаем, коммитим ...

# 2. Отправляем ветку
git push -u origin feature/new-book-format

# 3. Открываем Pull Request feature/new-book-format -> develop
#    PR триггерит CI (сборка без релиза) — зелёная галочка = можно мержить

# 4. Фича готова и проверена -> мержим в develop
```

## Выпуск релиза

Релиз собирается **автоматически при пуше в `master`**,
поэтому порядок такой:

```bash
# 1. Все фичи уже в develop. Забираем их в master
git checkout master
git pull
git merge develop          # или PR develop -> master и кнопка Merge

# 2. ОБЯЗАТЕЛЬНО поднимаем версию в PhotoBookRenamer.csproj
#    <Version>1.0.5</Version>   (версия должна быть БОЛЬШЕ последнего релиза)

# 3. Пуш в master -> CI собирает установщик -> создаёт GitHub Release
#    -> все клиенты получают предложение обновиться
git commit -am "Release 1.0.5"
git push origin master
```

### Что делает CI при пуше в master

1. Проверяет, что сборка идёт из `master` (иначе — отказ).
2. Проверяет, что версия **больше** последнего опубликованного релиза
   и что релиза с такой версией ещё нет. Иначе — отказ с понятным текстом.
3. Собирает проект, публикует `win-x64`, собирает установщик Inno Setup.
4. Создаёт GitHub Release с тегом `v<версия>`.
5. Обновляет установщик во всех предыдущих релизах
   (это нужно для клиентов, которые ещё не обновились).

Сборки **сериализованы**: если в `master` попало два коммита подряд,
вторая сборка дождётся первой и не прервёт её на середине.

## Ручной запуск релизной сборки

Вкладка **Actions -> Build and Release -> Run workflow**.

В поле `confirm` нужно ввести слово **`RELEASE`**.
Без этого сборка не запустится — защита от случайного прогона
из неправильной ветки.

---

## Сборочные пайплайны

| Файл | Что делает | Когда запускается |
|------|-----------|-------------------|
| `.github/workflows/build-and-release.yml` | Установщик + GitHub Release (**раздаётся клиентам**) | push в `master`, либо ручной запуск со словом `RELEASE` |
| `.github/workflows/ci.yml` | Только проверка сборки. Без установщика, без релиза | push в `develop`/`feature/*`/`fix/*`/`hotfix/*`/`release/*`/`chore/*` и PR в `master`/`develop` |

## Если нужно откатить клиентов

Откат — это **не** удаление релиза. `UpdateService.GetLatest()`
берёт самый свежий релиз, поэтому «откат» = выпуск новой версии
с предыдущим рабочим кодом.

1. `git checkout master && git revert <sha_сломанного_коммита>`
2. Поднять версию в `PhotoBookRenamer.csproj` выше текущей.
3. `git push origin master` — клиенты получат рабочую версию.
