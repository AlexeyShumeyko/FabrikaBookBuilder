# Ветки и выпуск

Коротко: **`master` — то, чем пользуются клиенты. `integration/2.0` — всё, из чего
получится 2.0.0.** Работа идёт во второй, релиз выходит из первой.

Основание и цена этого решения — в [docs/decisions/0003](docs/decisions/0003-branching-model.md).

---

## 1. Ветки

| Ветка | Что в ней | Когда меняется |
|---|---|---|
| `master` | только то, что у клиентов | при выпуске |
| `integration/2.0` | вся работа кампании | постоянно |
| `refactor/*`, `chore/*`, `spike/*`, `feature/*`, `fix/*` | одна задача | от `integration/2.0` и обратно в неё |
| `hotfix/*` | срочное для клиента | от `master`, в `master` и в `integration/2.0` |

**Правило, которое чаще всего нарушают:** задачу создаём от `integration/2.0`, а не от
`master`. Проверить можно одной командой: `git log --oneline -1` должен показывать
коммит из кампании.

## 2. Имена веток

Имя ветки — это её категория.

| Префикс | Для чего | Пример |
|---|---|---|
| `feature/<что>` | новая функция для пользователя | `feature/collapsed-books` |
| `fix/<что>` | ошибка, найденная на тесте или у клиента | `fix/save-index-on-exit` |
| `hotfix/<что>` | срочное: у клиента не работает | `hotfix/corrupt-export` |
| `refactor/<что>` | перестройка кода без изменения поведения | `refactor/extract-core` |
| `chore/<что>` | инфраструктура: пайплайн, доки, инструменты | `chore/release-guard-token` |
| `spike/<что>` | разведка: эксперимент, который может не войти вовсе | `spike/avalonia-startup` |

`spike/` — честная пометка «это опыт». Такие ветки не обязаны сливаться: их задача —
дать цифры для решения.

## 3. Порядок работы

Обычная задача:

```
integration/2.0 ──► fix/что-то
                       │  правка + все проверки
                       └──► слияние в integration/2.0
```

Выпуск:

```
integration/2.0 ──► поднимаем версию ──► pull request ──► master ──► релиз 2.0.0
```

Срочное для клиента:

```
master ──► hotfix/что-то
             ├──► слияние в master        (клиенты получают исправление)
             └──► слияние в integration/2.0 (иначе баг вернётся в 2.0.0)
```

Критерий «срочного»: **клиент не может выполнить работу**. Не «медленно», не
«неудобно» — именно не может. Всё остальное копится и выходит с 2.0.0.

## 4. Правила

1. **`master` в любой момент соответствует рабочей версии у клиента.**
2. **Ветка живёт не дольше двух недель** и удаляется сразу после слияния.
3. **Перед слиянием — все проверки** из [BUILD.md](BUILD.md), раздел 3.
4. **Шаг равен коммиту равен точке отката.** Не понравилось — шаг назад.
5. **Волны 0–2 не видны снаружи.** Клиенты на 1.x ничего не получают, пока не выйдет
   2.0.0.
6. **Контракт имён при выгрузке неприкосновенен.** `001-00.jpg` — это то, что ждёт
   печатный сайт. Меняется только с решением владельца продукта.

## 5. Как не превратить репозиторий в свалку веток

1. **Включить автоудаление.** GitHub → `Settings` → `General` → `Pull Requests` →
   **Automatically delete head branches**. После слияния ветка исчезает сама.
2. **Одна задача — одна ветка.** Не «фикс всего подряд», а `fix/одно-конкретное`.
3. **Не держать ветку после слияя.** Мёртвая ветка не ломает ничего, но через полгода
   их будет двадцать.

## 6. Язык

| Что | Язык |
|---|---|
| Текст в программе, заметки релизов, документация | русский |
| Сообщения коммитов, заголовки и описания пулреквестов, код и имена в коде | английский |

Причина простая: программой пользуются сотрудники компании, а репозиторий читают
разработчики.

## 7. Версии

Формат `MAJOR.MINOR.PATCH`.

| Изменение | Как версионируем |
|---|---|
| Исправление для клиента | `PATCH` — 1.1.2, 1.1.3 |
| Новое для пользователя | `MINOR` — 1.3.0 |
| Другая платформа или переписанный интерфейс | `MAJOR` — 2.0.0 |

Версия живёт в `PhotoBookRenamer.csproj` и в теге релиза `v<версия>`. Больше нигде.
Номер поднимается один раз, в момент выпуска: до этого в коде остаётся текущая версия.

Сборка релиза откажется собираться повторно для уже выпущенной версии — это защита от
двойного релиза, а не ошибка.
