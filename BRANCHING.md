# Ветки и релизы

Короткая модель: **`master` — единственная интеграционная и релизная ветка.** Всё
остальное живёт недольше одной задачи и удаляется после слияния.

Постоянных веток «под направления» у нас нет и не планируется. Ветка `develop`,
которая была в репозитории, выведена из обихорачивания: она отстала от `master` на 46
коммитов и не содержала ничего своего. Причина простая — две интеграционные ветки
означают двойные слияния и постоянный вопрос «а это уже в master или нет».

---

## 1. Правила

1. **`master` в любой момент запускается и работает.** Не «почти работает» — работает.
2. **Любое слияние в `master` — это релиз.** Сборка релиза запускается на push в
   `master`, поэтому каждое слияние требует поднятой версии в `PhotoBookRenamer.csproj`
   и пройденных проверок.
3. **Ветка живёт не дольше недели** и удаляется сразу после слияния.
4. **Перед слиянием — все проверки** из [BUILD.md](BUILD.md), раздел 3.
5. **Контракт имён при экспорте неприкосновенен.** `001-00.jpg` — это то, что ждёт
   принт-сайт.

## 2. Имена веток

Имя ветки — это её категория. Ничего больше знать не нужно.

| Префикс | Для чего | Пример |
|---|---|---|
| `feature/<что>` | Новая функция для пользователя | `feature/collapsed-books` |
| `fix/<что>` | Ошибка, найденная на тесте или у клиента | `fix/save-index-on-exit` |
| `hotfix/<что>` | Срочное: сломалось у пользователя, ждём релиза | `hotfix/corrupt-export` |
| `refactor/<что>` | Перестройка кода без изменения поведения | `refactor/extract-photo-core` |
| `chore/<что>` | Инфраструктура: пайплайн, доки, инструменты | `chore/release-guard-token` |
| `spike/<что>` | Разведка: эксперимент, который может не войти вовсе | `spike/avalonia-project-list` |

`spike/` — честная пометка «это опыт». Такие ветки не обязаны сливаться: их задача —
дать цифры для решения.

## 3. Порядок работы

```
master ──► feature/что-то      (правка + проверки)
              │
              └──► merge в master → релиз → ветка удаляется
```

Для срочного:

```
master ──► hotfix/что-то
              ├──► merge в master      (релиз уходит клиентам)
              └──► merge в рабочую ветку  (в тот же день, иначе баг вернётся)
```

## 4. Рефакторинг

Рефакторинг — это очередь коротких кусков, а не одна длинная ветка. Очередь живёт в
`doc/ROADMAP.md`, раздел 4.

| Правило | Почему |
|---|---|
| Кусок — 1–4 дня | Дольше одного рабочего окна — уже не кусок |
| Каждый кусок сливается и выпускается | В любой момент можно остановиться и иметь рабочую версию |
| Куски, невидимые снаружи, можно вливать во время пользовательского теста | Программа выглядит и ведёт себя так же |
| Куски, меняющие интерфейс, ждут обратной связи от теста | Нельзя менять то, что люди уже начали осваивать |

## 5. Как не превратить репозиторий в свалку веток

1. **Включить автоудаление.** GitHub → `Settings` → `General` → `Pull Requests` →
   **Automatically delete head branches**. После этого удалённая ветка исчезает сразу
   после слияния, и руками ничего удалять не нужно. Включено ли — проверить.
2. **Одна задача — одна ветка.** Не «фикс всего подряд», а `fix/одно-конкретное`.
3. **Не держать ветку после слияя.** Мёртвая ветка ничего не ломает, но через полгода
   их будет двадцать, и в списке не разберёшься.

## 6. Версии

Формат: `MAJOR.MINOR.PATCH` (`1.1.0`).

| Изменение | Как версионируем |
|---|---|
| Фикс для теста или клиента | `PATCH` — `1.1.1`, `1.1.2`, … |
| Изменения, которые видит пользователь | `MINOR` — `1.2.0` |
| Несовместимое изменение формата проекта или контракта имён | `MAJOR` — `2.0.0` |

Версия живёт в `PhotoBookRenamer.csproj` и в теге релиза `v<версия>`. Больше нигде.

Релиз `1.1.0` уже вышел, поэтому следующий фикс — `1.1.1`. Пока версия не поднята,
сборка релиза откажется собираться повторно: это защита от двойного релиза, а не ошибка.
