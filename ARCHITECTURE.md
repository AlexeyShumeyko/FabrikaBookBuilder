# Архитектура

Документ описывает, как устроена программа и почему именно так. Он правдив на момент
написания и меняется вместе с кодом — решения, из-за которых всё выглядит именно так,
лежат в [docs/decisions](docs/decisions).

Программа делает одну вещь: раскладывает фотографии по книгам и разворотам, присваивает
имена файлов и выгружает копии в папку для печати. Оригиналы фотографий никогда не
изменяются — программа только читает их и копирует по ссылкам.

**Состояние документа: 2026-10-03.** Разделы 1–5 описывают цель, к которой идёт
работа; сейчас код ещё один проект и разделы эти — проектное решение, а не описание
файлов на диске. Раздел 6 описывает то, что работает уже сегодня.

## 1. Слои

```
PhotoBookRenamer.sln
│
├── src/
│   ├── PhotoBook.Core/                  правила предметной области
│   ├── PhotoBook.Application/           сценарии и порты
│   ├── PhotoBook.Infrastructure/        работа с диском, сетью и картинками
│   ├── PhotoBook.Desktop.Wpf/           оболочка на WPF (временная)
│   └── PhotoBook.Desktop.Avalonia/      оболочка на Avalonia
│
└── tests/
    ├── PhotoBook.Core.Tests/
    ├── PhotoBook.Application.Tests/
    └── PhotoBook.Infrastructure.Tests/
```

**Правило, которое проверяет компилятор:** `Core` не ссылается ни на что, кроме себя.
Ни интерфейса, ни файловой системы, ни журнала. Проверить это руками невозможно —
проект `PhotoBook.Core` просто не имеет ссылок на другие проекты, и если кто-то добавит,
сборка упадёт.

Наружу слои общаются по правилам:

| Слой | Что содержит | Чего не содержит |
|---|---|---|
| `Core` | `Book`, `Page`, `Project`, раскладка разворотов, правила проверки папок, план выгрузки | UI, файлов, сети, журнала, `ObservableCollection` |
| `Application` | сценарии («добавить папки», «выгрузить», «проверить обновление») и **порты** | конкретных технологий |
| `Infrastructure` | реализации портов: диск, JSON, картинки, GitHub, журнал | UI и WPF |
| `Desktop.*` | представление, привязки, диалоги | правил предметной области |

Направление зависимостей — строго внутрь: `Desktop` → `Application` → `Core`.

## 2. Порты и адаптеры

`Application` объявляет интерфейсы, `Infrastructure` их реализует. Так решается, чем
именно является «файл» или «картинка»:

| Порт | Зачем | Реализация в WPF | Реализация в Avalonia |
|---|---|---|---|
| `IFileSystem` | работа с файлами и папками | `System.IO` | `System.IO` |
| `IThumbnailProvider` | маленькая превью-картинка | полное декодирование, медленно | Skia умеет уменьшать при чтении, быстро |
| `IPickFolder` | выбор папки пользователем | системное окно | окно Avalonia |
| `IProjectRepository` | чтение и запись проектов | JSON в `%LOCALAPPDATA%` | то же |
| `ILogSink` | журнал | файл и консоль | то же |
| `IUpdateFeed` | проверка обновлений | GitHub Releases | GitHub Releases |

Производительность — свойство адаптера, а не ядра. Один и тот же код дважды умеет
показывать превью: медленно и быстро. Это измерено, а не заявлено.

## 3. Правила, принятые в коде

| Правило | Почему |
|---|---|
| Ошибка — это значение, а не исключение | `Result<T>` возвращает текст ошибки; `catch` без `catch (Exception)` не остаётся |
| Долгая работа принимает `CancellationToken` | Закрыл окно — работа встала, а не доработала в фоне |
| Зависимости — через конструктор | Никаких `GetServiceProvider()` внутри моделей представления |
| Наблюдаемость — дело UI | `Core` отдаёт `IReadOnlyList<T>`, наблюдаемые коллекции живут в оболочке |
| Один способ сделать вещь | Путь к файлу превью, имя файла при выгрузке, текст ошибки считаются в одном месте |
| MVVM без ручного кода | Исходные генераторы вместо ручных `OnPropertyChanged` |

## 4. Что защищено контрактом

Эти вещи нельзя менять молча, потому что на них завязаны клиенты и печатный сайт:

| Контракт | Где живёт | Чем проверяется |
|---|---|---|
| Имя файла при выгрузке: `001-00.jpg` | `ExportService.GenerateFileName` | тест контракта |
| Формат файла проекта | `PhotoBook.Core` + `ProjectSerializer` | тест совместимости: проект 1.1.0 открывается и выгружается так же |
| Папка данных `%LOCALAPPDATA%\PhotoBookRenamer` | `Infrastructure` | ручная проверка |

## 5. Производительность: как с этим живём

Программа не декодирует оригинал фотографии, чтобы показать 190 пикселей. Исходные
файлы бывают по 24 мегапикселя, и «прочитать всё, потом уменьшить» — самая дорогая
операция в продукте.

| Сценарий | WPF-оболочка | Avalonia-оболочка |
|---|---|---|
| 20 книг по 9 фотографий, первый раз | ~42 с, пик 2,35 ГБ | цель: единицы секунд |

Замеры берутся скриптом `perf-open.ps1` в реальной программе, а не умозрительно.
Числа хранятся в `doc/ROADMAP.md`.
